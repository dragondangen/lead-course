# Решение по заявке и маршрут согласования

| | |
|---|---|
| Статус | Черновик, требует согласования с бизнесом |
| Поддомен | Enrollment (ядро), частично Courses |
| Дата | 2026-07-26 |

## 1. Контекст и проблема

Заявка на поток курса обрабатывается поэтапно. Сейчас эта обработка реализована с тремя существенными ограничениями:

1. **Этапы зашиты в код.** Последовательность «получена → на одобрении → согласована → одобрена» задана перечислением `ApplicationStatus` и картой переходов `AllowedTransitions`. Организация не может определить собственный порядок согласования.
2. **Решение не сохраняется как факт.** Есть единственное перезаписываемое поле `DecisionComment`. Предыдущие комментарии теряются, автор решения не фиксируется вообще, время решения известно только для последнего изменения.
3. **Заявитель не может повторить попытку.** После отказа заявка становится терминальной, а повторная подача блокируется проверкой «у пользователя уже есть заявка на этот поток».

Разным организациям нужны разные процедуры: крупному поставщику курсов требуется несколько ступеней согласования, небольшой школе — одна. Требуется вынести процедуру в настройку и сделать решение полноценной сущностью предметной области.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Маршрут согласования** | Упорядоченный набор этапов, который проходит заявка от подачи до финального решения |
| **Этап согласования** | Одна ступень маршрута; на этапе выносится ровно одно действующее решение |
| **Решение** | Зафиксированный исход этапа: «ок» либо «отклонено», с автором, временем и комментарием |
| **Переподача** | Создание новой заявки на основе ранее отклонённой или отозванной заявки того же пользователя |
| **Активная заявка** | Заявка, обработка которой не завершена (не отклонена, не одобрена, не отозвана) |

## 3. Требования

### 3.1. Маршрут согласования

**БТ-1.** Маршрут согласования задаётся для курса. Организация может определить маршрут по умолчанию, применяемый ко всем её курсам; курс вправе переопределить его собственным.

**БТ-2.** Маршрут состоит из упорядоченного списка этапов. Маршрут должен содержать хотя бы один этап.

**БТ-3.** Этап содержит наименование, отображаемое заявителю и модератору, и указание, кто уполномочен выносить решение на этом этапе.

**БТ-4.** Заявка при подаче фиксирует маршрут в том виде, в каком он действовал на момент подачи. Последующее изменение маршрута не влияет на заявки, поданные ранее.

> Требование БТ-4 является обязательным. Без него изменение маршрута приведёт к тому, что заявки в работе окажутся в несуществующем этапе, а уже вынесенные решения — привязанными к удалённым ступеням.

**БТ-5.** Изменение маршрута допускается в любой момент и вступает в силу только для заявок, поданных после изменения.

**БТ-6.** Маршрут, по которому имеются заявки в работе, не может быть удалён.

### 3.2. Решение по заявке

**БТ-7.** На каждом этапе маршрута выносится решение с одним из двух исходов: «ок» либо «отклонено».

**БТ-8.** Решение фиксирует: этап, исход, пользователя, вынесшего решение, дату и время, комментарий.

**БТ-9.** При исходе «отклонено» комментарий обязателен. При исходе «ок» комментарий необязателен.

**БТ-10.** Решения выносятся строго в порядке следования этапов маршрута. Вынести решение по этапу, предшествующий которому не пройден, невозможно.

**БТ-11.** Исход «отклонено» на любом этапе завершает обработку заявки. Последующие этапы не выполняются, заявка получает статус «отклонена».

**БТ-12.** Исход «ок» на последнем этапе маршрута означает одобрение заявки: заявителю выделяется место на потоке.

**БТ-13.** История решений неизменна. Вынесенное решение не может быть отредактировано или удалено.

**БТ-14.** Заявитель видит текущий этап своей заявки и исходы завершённых этапов, включая комментарии к отказам.

### 3.3. Переподача заявки

> **Уточнение принятого решения.** Рассматривались два способа дать заявителю вторую попытку: пересмотр ранее вынесенного решения по существующей заявке либо подача новой заявки. Принят второй вариант. Ранее вынесенные решения остаются неизменными (см. БТ-13), а новая попытка оформляется отдельной заявкой.

**БТ-15.** Заявитель вправе подать новую заявку на тот же поток, если его предыдущая заявка была отклонена или отозвана.

**БТ-16.** Новая заявка содержит ссылку на предыдущую, что позволяет проследить всю цепочку попыток.

**БТ-17.** Предыдущая заявка остаётся в терминальном статусе и не изменяется.

**БТ-18.** Переподача невозможна, если у заявителя есть активная заявка на этот поток.

**БТ-19.** Переподача невозможна, если предыдущая заявка была одобрена: заявитель уже получил место.

**БТ-20.** Переподача подчиняется общим правилам подачи заявки: приём на поток должен быть открыт.

**БТ-21.** Новая заявка проходит маршрут согласования заново, начиная с первого этапа, по маршруту, действующему на момент переподачи.

## 4. Сводка инвариантов

| Инвариант | Требование |
|---|---|
| Маршрут содержит не менее одного этапа | БТ-2 |
| Заявка исполняет маршрут, зафиксированный при подаче | БТ-4 |
| Этапы проходятся по порядку, без пропусков | БТ-10 |
| Отказ на этапе завершает обработку | БТ-11 |
| Комментарий обязателен при отказе | БТ-9 |
| Решение неизменно после вынесения | БТ-13 |
| Одновременно активна не более одной заявки на поток | БТ-18 |

## 5. Влияние на существующую модель

Реализация требований затрагивает текущую доменную модель следующим образом.

**Перечисление `ApplicationStatus` перестаёт кодировать этапы.** Значения `Agreed` и `NotAgreed` описывают исход второй ступени фиксированной процедуры и несовместимы с настраиваемым маршрутом: при трёх этапах согласования назвать их невозможно. Статус заявки становится обобщённым — получена, в обработке, одобрена, отклонена, отозвана, — а сведения о текущем этапе выносятся в отдельный атрибут.

**Поле `DecisionComment` упраздняется.** Его заменяет коллекция решений.

**В домене появляется модератор.** Требование БТ-8 обязывает фиксировать автора решения. В настоящий момент идентификатор пользователя, принимающего решение, не передаётся ни в один метод обработки заявки.

**Проверка «у пользователя уже есть заявка» уточняется.** Согласно БТ-18 она должна учитывать только активные заявки; наличие ранее отклонённой заявки не препятствует переподаче.

**Появляется новое понятие в поддомене Courses.** Маршрут согласования принадлежит курсу либо организации и требует отдельного места в модели.

## 6. Открытые вопросы

Требуют решения бизнеса до начала реализации.

1. **Ограничение числа попыток.** Допустимо ли неограниченное количество переподач? Требуется ли период ожидания между попытками? Без ограничения возможна ситуация, когда заявитель подаёт заявки непрерывно.
2. **Уполномоченный на этапе.** Кто выносит решение — конкретный сотрудник, роль в организации или любой её сотрудник? От ответа зависит модель прав доступа.
3. **Возврат на предыдущий этап.** Допустим ли возврат заявки на доработку без отказа? Текущая редакция требований такой возможности не предусматривает.
4. **Наследование данных при переподаче.** Переносятся ли в новую заявку сведения из предыдущей — сопроводительный текст, приложенные документы?
5. **Уведомление о смене этапа.** Уведомляется ли заявитель о прохождении каждого этапа или только о финальном решении?
